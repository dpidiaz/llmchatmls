# MLS R4.3 Worker Command — ejecución de `MLS R43 siguiente`

> **R44 CUTOVER NOTE (2026-10-01):** this GitHub/Library control plane is legacy fallback. After R44 production deployment, new disposable-chat production uses `MLS R44 siguiente` with Cloudflare Worker + D1. Legacy schedulers are manual-only; do not use this command for new high-concurrency work.

Este documento define la ejecución técnica exclusiva de **`MLS R43 siguiente`**.
`MLS R32 EDITORIAL/r4 snapshot command.cjs` ya no tiene fallback a R4.2.

El usuario no debe escribir ningún subcomando, SHA, número de reserva, Wave Issue
ni shard. El chat resuelve todo desde GitHub y conserva como autoridad únicamente
los objetos durables del protocolo.

## Regla principal

Una Wave R4.3 remota posee hasta **50 shards de 5 entradas** (máximo 250 entradas).
Pueden coexistir hasta **2 waves no reconciliadas**. Cada request válido recibe
**inmediatamente** el siguiente shard FIFO de cinco entradas: el worker no espera
a que aparezcan los otros 49 chats ni a que la Wave llegue a 50/50.

Un request nuevo conserva ownership productivo por 30 minutos, sin heartbeat ni
renew. Si ese chat desaparece, otro chat puede recuperar el shard mediante takeover.
Los requests legacy creados antes de este contrato no tenían ownership productivo
y son recuperables inmediatamente.

Cada worker:

1. obtiene una admisión durable;
2. recibe exactamente un shard inmutable de cinco códigos;
3. produce esas cinco entradas;
4. no escribe GitHub mientras produce;
5. al terminar publica un único delta comprimido en su mismo request Issue;
6. no convierte `PRODUCED` en `VERIFIED`;
7. termina ese shard.

R33, evidencia, APA 7 y validación canónica siguen siendo obligatorios.

## Entrada única

El único comando visible para Snapshot Farm R4.3 es:

`MLS R43 siguiente`

`MLS BCR siguiente` pertenece a R4.2 y no es alias de este comando.

El chat lee el estado actual y llama conceptualmente a:

`snapshot command.route(issues, state)`

No reconstruir ownership desde memoria conversacional.

## Regla de conteo: admisión ≠ resultado

Durante `collecting`, `admissionCount` crece incrementalmente y cada admisión
ya puede estar produciendo o incluso haber publicado RESULT. En una Wave `sealed`,
**`workerCount/workerCount` significa únicamente que ya existen todos los requests**.
Para la wave 50×5, `50/50` no implica que existan 50 resultados durables.

El router debe exponer y el chat debe respetar tres campos distintos:

- `admissionCount`: shards admitidos;
- `durableResultCount`: shards con RESULT durable válido;
- `missingShardIds`: shards admitidos que todavía no tienen RESULT durable.

Nunca declarar “20/20 resultados”, “todo durable” o “listo para reconciliar” basándose
solo en `status=sealed`, en el número de requests o en `admission.assignments.length`.

Solo cuando `durableResultCount === admissionCount` y `missingShardIds.length === 0`
puede usarse `await_reconciliation`.

## Estados del adapter

### `create_request`

La Wave está `collecting` y este intento aún no posee request durable.

Crear exactamente un Issue con `createRequestEnvelope(...)`, pasando el
`waveIssueNumber` elegido por el router cuando haya más de una wave activa:

- título `[MLS BCR R4.3][REQUEST] <requestId>`;
- marcador `MLS_BCR_R43_REQUEST`;
- `waveIssueNumber`, `waveId` y `waveHash` exactos;
- un `requestId` único y estable para este intento.

Después releer el Issue creado y conservar su número. Al volver a ejecutar el
router con ese `requestId` + número de Issue, el resultado normal es
**`produce_shard` inmediatamente**, aunque la Wave siga `collecting`.

No crear un segundo request si el primero tiene resultado incierto; recuperar por
el mismo `requestId`.

### `await_seal`

Los `workerCount` requests ya existen pero el scheduler aún no ha persistido la
transición `collecting → sealed`. Es una carrera corta del control plane, no una
barrera de producción: los workers admitidos ya pudieron producir y publicar RESULT.

### `create_takeover`

Un request legacy o un ownership productivo expirado todavía no tiene RESULT y
este chat nuevo puede recuperarlo. Esto puede ocurrir tanto en `collecting` como
en `sealed`.

**No buscar ni regresar al chat viejo.** Crear exactamente un Issue temporal de takeover
con `createTakeoverEnvelope(...)`:

- título `[MLS BCR R4.3][TAKEOVER] <takeoverId>`;
- marcador `MLS_BCR_R43_TAKEOVER`;
- shard objetivo y request Issue original fijados por el router;
- TTL por defecto: 30 minutos;
- sin renew, heartbeat ni checkpoint.

Después releer GitHub y volver a ejecutar el router con el mismo `takeoverId` y el
número del takeover Issue.

Si dos chats crean claims para el mismo shard desde una vista simultánea, gana el
Issue con número menor. El otro recibe `takeover_retry` y debe crear un
`takeoverId` nuevo para el siguiente shard disponible.

### `takeover_retry`

Este claim perdió una carrera contra otro takeover de menor número de Issue.

No producir el shard. Crear un nuevo takeover con un `takeoverId` distinto y
releer el estado. No hay error de corpus ni de evidencia.

### `takeover_expired`

El claim superó su TTL sin publicar resultado.

No producir con ese claim. El shard vuelve a quedar disponible y puede ser
recuperado por otro chat nuevo mediante `create_takeover`.

### `superseded_by_takeover`

El chat original reapareció, pero otro chat posee un takeover vigente sobre su shard.

El chat original no debe producir ni publicar resultado mientras ese takeover siga
vigente. Esto evita producción duplicada.

### `takeover_capacity_full`

Todos los shards todavía incompletos tienen un takeover vigente.

No crear claims adicionales en ese instante. Cuando un takeover publique resultado
o expire, el estado volverá a cambiar.

### `await_reconciliation`

Todos los shards de esa wave ya tienen resultado durable. No producir más; esperar
la reconciliación y el auto-handoff R33.

### `produce_shard`

El request ya pertenece al prefijo FIFO de admisión incremental. La Wave puede
seguir `collecting` o estar `sealed`: **no se espera 50/50 para producir**.

Usar exclusivamente el `workerContext` devuelto por el adapter:

- `snapshotHash`;
- `waveHash`;
- `shardId`;
- cinco `codes`;
- paths de contenido y Evidence;
- política `remoteWritesDuringProduction=false`.

Durante producción:

- investigar y redactar exclusivamente esos cinco códigos;
- cada entrada debe tener Evidence real y revisión por fuente;
- recalcular identidades R33 cuando una afirmación cambie;
- conservar assessment `PENDING_CANONICAL_R33_VALIDATION` hasta el gate canónico;
- no leer un estado previo `VERIFIED` como sustituto de verificación;
- no escribir Issues, ramas, commits, renews, heartbeats ni checkpoints GitHub.

El resultado local debe formar un `MLS-BCR-DELTA-1` válido con:

- `entries`;
- `checkpoints`;
- `reviews`;
- exactamente los cinco códigos del shard;
- `snapshotHash`, `waveHash` y `shardId` correctos.

Al terminar, crear el envelope mediante
`createResultEnvelope(...)`. Este valida que el delta pertenece al shard
admitido y produce el body comprimido `MLS_BCR_R43_RESULT`.

Actualizar **ese mismo request Issue una sola vez** con el resultado.

### `result_already_submitted`

El mismo Issue ya contiene un delta válido para el shard admitido.

No volver a producir, no sobrescribir y no publicar otro resultado. Tratar la
entrega como durable e idempotente.

### `request_not_admitted`

Existe un `requestId`, pero quedó fuera de los primeros `workerCount` requests
válidos de la Wave.

No producir. No sustituirlo por otro request dentro de la misma Wave. Conservar el
Issue como evidencia del intento y terminar sin ownership.

### `no_active_r43_wave`

No existe una Wave R4.3 activa autoritativa.

No abrir R4.2, no crear un Issue R4.2 y no reinterpretar el comando. Informar que
no hay Wave R4.3 activa y terminar sin adjudicación.

R4.2 solo se ejecuta mediante su comando separado: `MLS BCR siguiente`.

## Autoridad de Wave

Solo se acepta una Wave Issue que:

- esté abierta;
- haya sido creada por `github-actions[bot]`;
- tenga título `[MLS BCR R4.3][WAVE][...]`;
- contenga exactamente un marcador `MLS_BCR_R43_WAVE`;
- pase el hash y los validadores del contrato.

Puede haber más de una Wave activa. El router mantiene **afinidad estricta** para
request/takeover existentes y, para un chat nuevo, elige determinísticamente la wave
con más capacidad accionable. Así una wave con pocos stragglers no bloquea la siguiente.

Los códigos siguen aislados por reservas durables; un solapamiento entre waves falla
cerrado. Un Issue creado manualmente por otro usuario no puede secuestrar el routing.

## Persistencia mínima Route B

Para cada worker de una wave remota:

- 1 creación de request Issue, que activa el shard inmediatamente;
- 0 escrituras GitHub durante producción;
- 1 actualización final del mismo Issue con el delta, conservando también el
  marcador REQUEST para que el scheduler pueda sellar la Wave después.

No existen REQUEST/LEASE/RENEW/CHECKPOINT/COMPLETE por bloque como en R4.2.

La Wave Issue cambia únicamente al sellar admisión y al reconciliar resultados.

## Reconciliación

El scheduler puede recibir resultados mientras la Wave sigue `collecting`.
Cuando aparecen los `workerCount` requests, sella la admisión usando el mismo orden
FIFO ya utilizado por los workers. Después marca la Wave como reconciliada cuando
existen exactamente los `workerCount` deltas válidos y cada Issue entrega su shard.

Un delta faltante mantiene la Wave en espera. Un delta de otro shard, hash inválido,
Wave equivocada o Issue ajeno falla cerrado.

Después de reconciliar, el auto-handoff R4.3 → R33 activa esa wave sin esperar a
que otras waves terminen. R33 puede mantener varias identidades de handoff activas,
siempre disjuntas, y distribuye microclaims de 5 entre ellas. La integración final
sigue serializada y acotada.

`PRODUCED`, `reconciled` o `submitted` no significan `VERIFIED`.

## Emergency anti-idle fallback

Hard invariant: `MLS R43 siguiente` must not return an idle outcome merely because
GitHub's control plane is rate-limited or because the allocator reports `NO_WORK`
while useful non-mutating work remains.

### Trigger

Activate the emergency path immediately when any GitHub mutation needed for
REQUEST, TAKEOVER, RESULT, sealing, reconciliation or handoff returns HTTP 403/429
for a secondary rate limit, or when `NO_WORK` is attributable to control-plane
availability rather than exhaustion of useful MLS work.

Do not retry GitHub mutations in a burst. Respect `Retry-After`; otherwise back off
before retrying and increase the delay exponentially. GitHub mutations must remain
serialized and deliberately spaced. Do not open more GitHub-backed waves merely to
escape a throttled control plane.

### Emergency control plane — current contract

The emergency control plane is persistent ChatGPT Library staging. GitHub remains
the canonical corpus and final publication destination.

Authoritative Library paths:

- `/MLS BCR R43/emergency/README.md`
- `/MLS BCR R43/emergency/pool-manifest.json`
- `/MLS BCR R43/emergency/buckets/b00.json` … `b3f.json`
- `/MLS BCR R43/emergency/results/<ticketId>.md`

Current frozen boundary:

- base commit: `2961a29cfcb62caa9972e5dc5552037b001063a3`
- verified-index blob SHA: `e19bc5f617a93f4b1ec50eb96815783ba6b8920e`
- candidate domain: pending entries matching `MLS-V03` through `MLS-V09`
- pending candidates at freeze: **6,048**
- reserved positions: **4,000**
- logical tickets: **800**
- ticket size: **5 entries**
- bucket ledgers: **64**
- claim TTL: **45 minutes**
- storage mode: **64 independent CAS bucket ledgers**
- execution mode: **read-only evidence audit**
- canonical publication: **GitHub only**

The 4,000 reserved positions are deterministic ordinals 1…4000 inside the frozen
pending candidate set. Resolve a logical ticket by reading the frozen
`content/manifest.json` in manifest order, keeping only codes matching
`^MLS-V0[3-9]-` that are absent from the frozen verified index, numbering the
result from 1, and assigning each ticket its inclusive five-ordinal range.

This leaves **2,048** frozen V03–V09 candidate positions outside the currently
reserved emergency pool.

### Claim protocol

Emergency tickets are logical records distributed across 64 bucket ledgers instead
of 800 independent files or one global `nextShard++` counter.

A claimant must:

1. read one bucket and its current Library version;
2. select a `free` ticket, or an expired `claimed` ticket;
3. claim it with a compare-and-swap replacement using the version that was read;
4. on CAS conflict, discard the speculative claim, reread and retry;
5. bind the claim to a unique claimant id plus `claimedAt` and `expiresAt`;
6. audit exactly the five entries owned by that ticket;
7. persist the durable bundle at
   `/MLS BCR R43/emergency/results/<ticketId>.md`;
8. CAS-update the bucket ticket to `done` with the result path/hash.

The 64-bucket layout spreads 100–200 simultaneous chats over independent control
files and avoids turning one Library file into another global bottleneck.

### Emergency work contract

During emergency execution:

1. do not create a GitHub Issue merely to obtain ownership;
2. do not open additional GitHub-backed waves while secondary limiting is active;
3. prefer an already-owned R4.3 shard if it can continue with zero GitHub writes;
4. otherwise claim one emergency Library ticket using the CAS protocol above;
5. read canonical entry/evidence data from GitHub without mutating it;
6. audit linguistic accuracy, evidence gaps, source quality, APA 7, contradictions,
   unsupported claims and proposed corrections;
7. perform zero GitHub writes during production;
8. persist the audit result durably in Library staging;
9. never treat `PRODUCED`, `AUDITED` or a Library result as `VERIFIED`;
10. later, a serialized drainer may integrate accepted findings into GitHub after
    conflict checks and canonical R33 validation.

### Priority order

When the normal path is healthy:

- finish already-owned R4.3 shards first;
- recover missing admitted shards next;
- admit new R4.3 shards only while GitHub mutations are healthy.

When GitHub mutations are throttled:

- continue any already-owned shard with zero remote writes;
- otherwise claim emergency Library work immediately;
- defer RESULT/reconciliation/handoff publication until the GitHub cooldown clears.

The visible response `sin work` is reserved only for true useful-work exhaustion,
not for a GitHub bottleneck.

### Current implementation boundary

The emergency pool and its Library control plane already exist. The repository-side
`MLS R43 siguiente` command **does not yet automatically invoke ChatGPT Library**
as a machine-level fallback. Until that adapter is wired, a capable chat/agent must
follow this documented routing contract when normal GitHub admission is blocked.

Do not state that the fallback is fully automatic until the repository code has a
tested Library adapter or an equivalent shared control-plane implementation.

### 2026-09-30 — Secondary Rate Limit anti-idle expansion

Observed condition:

- repeated `MLS R43 siguiente` chats returned `sin work` while useful corpus work
  still existed;
- GitHub control-plane mutations encountered HTTP 403 Secondary Rate Limit;
- existing remote waves still contained useful assigned/missing work, proving that
  the idle outcome could reflect allocator/control-plane pressure rather than true
  corpus exhaustion.

Decision:

- GitHub stays canonical but must not be required for every emergency ownership
  decision;
- high-concurrency fallback work is staged in ChatGPT Library;
- emergency production is read-only with respect to GitHub;
- GitHub mutations remain serialized after cooldown instead of being amplified by
  opening more GitHub-backed waves.

Change applied:

- replaced the earlier provisional 200-ticket / 1,000-position emergency design;
- reserved **4,000 deterministic positions**;
- created **800 logical tickets × 5 entries**;
- distributed them across **64 CAS bucket ledgers**;
- set claim TTL to **45 minutes**;
- froze the emergency domain at base commit
  `2961a29cfcb62caa9972e5dc5552037b001063a3`;
- used verified-index blob
  `e19bc5f617a93f4b1ec50eb96815783ba6b8920e`;
- candidate domain is pending V03–V09 only, with **6,048** candidates at freeze;
- removed the obsolete partial per-ticket-file structure;
- result bundles are staged under
  `/MLS BCR R43/emergency/results/<ticketId>.md`.

Reason:

The design permits many simultaneous chats to do useful, non-mutating R33 evidence
work without converting GitHub Issues or one shared counter into the throughput
bottleneck. It preserves the invariant that staged work is not canonical and is not
VERIFIED until the normal R33 integration gates pass.
