# MLS BCR R4.3 — Pilot 20 x 5

Status: **prepared / not activated**

Target: 20 concurrent ChatGPT Chat workers, 5 entries per worker, 100 total entries.

## Purpose

Prove that Snapshot Farm can match R33 quality while removing GitHub from the
worker hot path.

## Fixed constraints

- SOLO CHAT. No ChatGPT Work.
- FREE ONLY. No OpenAI API or other paid AI APIs.
- No Cloudflare/D1 editorial coordination.
- GitHub remains canonical.
- Same R33 source-to-claim review and canonical validators as R4.2.
- Produced is not VERIFIED.
- No worker may write to GitHub during shard production.

## Wave initialization

1. Read current canonical R33 state and active ownership.
2. Create four existing-format 25-entry buffered reservations under the serialized
   dispatcher. These 100 codes become durable `reservedCodes`, so R4.2/R33 cannot
   allocate them elsewhere.
3. Freeze:
   - GitHub base commit SHA;
   - content manifest blob SHA;
   - 100 reserved units.
4. Create `MLS-BCR-SNAPSHOT-1`.
5. Create one 20-worker `MLS-BCR-WAVE-1`, shard size 5.
6. Initialize the Chat allocator state for W0001..W0020.

No production starts if any reservation, snapshot hash or wave hash is ambiguous.

## Worker UX

The target user-facing command remains exactly:

`MLS BCR siguiente`

The chat-side adapter must:

1. claim one free shard through CAS against the shared ChatGPT allocator;
2. obtain its immutable Worker Context;
3. research and produce only those five entries;
4. persist one immutable delta locally / in the approved ChatGPT file surface;
5. CAS-complete the shard using its exact claimId + deltaHash;
6. stop. No GitHub REQUEST, LEASE, RENEW or COMPLETE.

If the CAS write conflicts, reread and retry allocation. Never infer ownership from
conversation memory.

## Recovery

A claimed shard expires only through the allocator contract. Reaping changes the
allocator revision, so a stale worker cannot later complete against the new state.

A recovered shard may be recomputed. Duplicate deliveries are not silently chosen:
the reconciler reports duplicate shard/delta hashes and the wave fails closed until
resolved.

## Reconciliation

The pilot is complete only when:

- W0001..W0020 each have exactly one accepted delta;
- 100 unique codes are present;
- no cross-shard code overlap exists;
- snapshotHash/waveHash match;
- every entry/checkpoint/review payload exists;
- no target path changed incompatibly since the frozen GitHub base.

Then build one immutable `MLS-BCR-GROUPED-SYNC-1` bundle.

## R33 quality gate

Before any canonical synchronization:

- run the same canonical R33 structural/evidence validators;
- source review must be real and complete;
- unsupported claims are repaired, not relabeled;
- every repair creates a new evidence identity where required;
- no status is promoted to VERIFIED merely because the worker finished.

A pilot quality failure does not fall back to weaker validation. It blocks the pilot.

## Metrics

Record at least:

- entries attempted;
- entries with durable deltas;
- duplicate shard attempts;
- allocator CAS conflicts;
- lost outputs;
- R33 first-pass successes;
- entries requiring repair;
- unresolved R33 failures;
- GitHub writes during worker production;
- total GitHub initialization/sync operations;
- elapsed production time per shard where observable.

### Required safety results

- accepted duplicate ownership: **0**
- lost accepted deltas: **0**
- GitHub writes during worker production: **0**
- R33 validator bypasses: **0**
- overwritten base conflicts: **0**

## Advancement

Only after this pilot completes cleanly:

1. 50-worker / 250-entry wave;
2. 100-worker / 500-entry wave;
3. make R4.3 eligible as the default backend behind `MLS BCR siguiente`.

R4.2 remains the rollback path until those gates pass.
