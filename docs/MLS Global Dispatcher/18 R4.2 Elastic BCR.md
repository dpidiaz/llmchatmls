# MLS R4.2 — Elastic Buffered Evidence Farm (chats desechables)

**Política permanente:** SOLO CHAT · FREE ONLY · GitHub canónico · R33 académico AI-only · APA 7 · sin ChatGPT Work, OpenAI API, APIs de pago, D1 editorial ni Cloudflare editorial. Circuito opt-in, aditivo a R4.1; no cambia «MLS siguiente» de R4. Preservar #1881.

## Comando universal

En CUALQUIER chat nuevo escribir **MLS BCR siguiente**. El chat debe crear su propia solicitud del Dispatcher, recuperar el claim exclusivo y finalizar su bloque en ese mismo chat, sin necesitar volver a otra conversación. Nadie debe recordar reserva, bloque o commit. El Dispatcher es dueño de la asignación y los chats se desechan después del commit confirmado. No existe ejecución autónoma de nuevos chats: el usuario abre las conversaciones.

Crear exactamente un Issue OWNER/MEMBER/COLLABORATOR titulado:

    [MLS Dispatcher][BCR][REQUEST] bcr-chat-<identificador-unico>

Contenido obligatorio:

    <!-- MLS_BCR_ELASTIC_COMMAND
    {"kind":"mls_bcr_elastic_command","version":1,"action":"next","requestId":"bcr-chat-YYYYMMDDTHHMMSS-<nonce-unico>"}
    -->

No inventar identidades asignadas. El Scheduler existente es SERIALIZADO con concurrency.group mls-global-dispatcher; procesa máximo cinco solicitudes por ejecución, con techo inicial de diez bloques activos. La reserva tiene 25 entradas en cinco bloques de cinco. Si todas las reservas están ocupadas y queda cupo global, obtiene una reserva adicional por ejecución mediante el allocator canónico R33 y un Context Pack 0/25. Excluye VERIFIED, DONE, STAGED, RESERVED, otros workers y recoveries. #1881 (bootstrap 0/25) tiene prioridad.

Una solicitud no admitida por falta de capacidad termina CAPACITY_BUSY sin consumir lease; una solicitud con más de dos minutos termina STALE. Así, 90 chats pueden emitir el mismo comando sin que 90 escritores simultáneos saturen GitHub. Reemitir el comando en otro chat cuando no haya cupo; nunca adjudicar silenciosamente un lease a un chat descartado.

## Claim exclusivo

Cuando el Issue pasa a título [MLS Dispatcher][BCR][LEASED], leer el marcador MLS_BCR_ELASTIC_CLAIM del cuerpo: reservationIssueNumber, block (1..5), cinco códigos, claimIssueNumber, leaseEpoch, branch, baseSha y expiresAt. Verificar siempre el Issue [MLS Buffered][RESERVED] y su estado elastic.blocks, así como la ref remota. El epoch corresponde al Issue, no al chat.

TTL por bloque: cinco minutos. Si la revisión tarda más, renovar antes del vencimiento (abajo). NUNCA escribir después de perder titularidad.

Solo escribir en la rama generacional entregada, por ejemplo r42/work/1881/01/1882, con force:false después de verificar HEAD == baseSha. No tocar master buffer r41/buffer/1881, main o la rama de otro worker. La ruta DURABLE del bloque dentro de esa rama es:

    r42-buffer/<reserva>/blocks/<NN>/
       chunk-NN-of-05.json
       entries/<codigo>.json            (cinco)
       checkpoints/<codigo>.json        (cinco)

El diff FINAL respecto a la rama maestra contiene exactamente esos once archivos. Para minimizar pérdidas de un chat caído, se admiten commits parciales agrupados de entrada+checkpoint en la rama exclusiva (con lectura remota después de cada confirmación); el chunk final se escribe después. Si la cuota Github está bajo presión, se puede producir el bloque de cinco en un solo commit, aceptando que trabajo NO persistido se pierde al caerse el chat. Cada checkpoint contiene hash real del Evidence individual. El chunk pasa bcr.verifyChunk contra manifest autorizado. Cada entrada exige revisión propia de afirmaciones académicas, artículos del snapshot fijado, registro bibliográfico, localizadores y APA 7, con provenance generatedWithAI:true, reviewerType:"chatgpt" y review:null. Fuente compartida no implica verificación heredada.

Ante GitHub 403/429: detener, preservar progreso previamente confirmado y NO reintentar en bucle.

### Renovar si todavía se trabaja

Abrir Issue con título [MLS Dispatcher][BCR][RENEW] <nonce>, autor original del claim y marcador:

Los números de arriba SON EJEMPLOS: sustituirlos por los campos reales. El Scheduler comprueba autor, epoch y vencimiento, y publica un nuevo expiresAt (+5 minutos). Si ya expiró, el chat antiguo NO posee permiso para publicar; abrir otro chat con el comando universal y recuperar el bloque.

### Completar con commit verificado

Al confirmar el SHA remoto de la rama del claim, abrir otro Issue del mismo autor, título [MLS Dispatcher][BCR][COMPLETE] <nonce>, con marcador:

    <!-- MLS_BCR_ELASTIC_COMMAND
    {"kind":"mls_bcr_elastic_command","version":1,"action":"complete","requestId":"bcr-complete-<nonce>","claimIssueNumber":1882,"reservationIssueNumber":1881,"block":1,"headSha":"<SHA-confirmado-de-40-hex>"}
    -->

El Scheduler coteja autor, leaseEpoch vigente, HEAD remoto, once Git blobs, chunk/hash, cinco checkpoint hashes, códigos exclusivos y perímetro de archivos. Solo después marca DONE en la reserva, y cierra el claim y COMPLETE. No hereda resultados académicos ni afirma Gate canónico PASS.

## Recuperación y consolidación automática

Al expirar un lease, el Scheduler conserva la rama y su HEAD; si hubo cambios verifica perímetro exclusivo antes de ofrecer su HEAD a un nuevo claim en rama GENERACIONAL nueva. El worker antiguo queda invalidado por epoch. No se sobreescriben ramas viejas ni checkpoints ajenos.

Cuando los cinco bloques están DONE, el Dispatcher ejecuta bcr.advance de 01 a 05 reconstruyendo el Context Pack y Source Index con registry canónico (sin heredar VERIFIED), y publica un ÚNICO commit agrupado en r41/buffer/<reserva> mediante HEAD optimista y sin force. El estado pasa a JOINED_AWAITING_CANONICAL_R33_GATE, nunca SEALED automáticamente. El Gate R33 independiente, sellado, SYNC e integración editorial siguen siendo exigibles. Cloudflare no se despliega automáticamente.

## Límite de capacidad y honestidad operativa

MAX_ACTIVE=10 y MAX_REQUESTS_PER_TICK=5 son límites conservadores iniciales. Abrir 90 chats implica hasta 90 SOLICITUDES, no 90 escritores GitHub simultáneos; el Dispatcher puede emitir CAPACITY_BUSY y ningún chat debe fingir trabajo asignado. No hay dependencia entre conversaciones y ninguna API pagada.

La reserva #1881, todavía 0/25 al realizar la migración, conserva sus nueve archivos y su titularidad. El circuito legacy R4.1 no se modifica retroactivamente; R4.2 es aditivo.
