# MLS R33 siguiente — gate canónico R4.3 → R33

## Alcance

Este comando existe exclusivamente para cerrar el gate R33 de la Wave R4.3 #2208.

Comandos distintos:

- `MLS BCR siguiente` → R4.2.
- `MLS R43 siguiente` → producción Snapshot Farm R4.3.
- `MLS R33 siguiente` → validación/evidencia canónica de las 100 unidades reconciliadas de #2208.

No intercambiar ni usar como aliases.

## Invariante principal

El gate #2208 tiene ownership durable mediante las reservas R4.3 y un handoff R33 activo.
R4.2 permanece bloqueado.

Cada claim R33 debe contener simultáneamente:

- `provider: "r33-farm"`
- `workPrefix: "r33-handoff:2208:"`

Un claim que no tenga ambos filtros no pertenece a este gate.

## Chat nuevo / descartable

Un chat nuevo con `MLS R33 siguiente`:

1. genera `requestId` y `workerId` únicos;
2. llama conceptualmente a `r4 r33 gate command.createClaim(...)`;
3. crea un único Issue `[MLS Dispatcher][CLAIM] <requestId>`;
4. relee el mismo Issue después del Scheduler;
5. llama a `inspectAssignment(issue)`;
6. solo trabaja si devuelve `action: process_r33`.

El chat no necesita localizar conversaciones anteriores.

## Assignment válido

El adapter falla cerrado salvo que:

- el Issue sea `[MLS Dispatcher][LEASED]`;
- `provider === "r33-farm"`;
- `workId` empiece exactamente con `r33-handoff:2208:`;
- los locks contengan un microclaim R33 acotado;
- la rama y lease provengan del Global Dispatcher.

Recoveries R33 históricas y backlog general quedan fuera del scope de este comando.

## Producción R33

Seguir exactamente las instrucciones del assignment.

Para cada entrada:

1. trabajar solo en el `evidenceArtifactPath` permitido;
2. usar el artículo canónico actual indicado por `contentPath`;
3. crear/reparar Evidence real: claims sustanciales, Source Registry normalizado, EvidenceLinks, locators cuando la policy los exige, APA 7 válido y contradicciones explícitas;
4. no promocionar a VERIFIED por haber terminado;
5. ejecutar antes de cada commit: `node scripts/R4-evidence-preflight.cjs <ruta-evidence>`;
6. ejecutar la validación requerida del assignment;
7. hacer commit en la rama asignada;
8. emitir CHECKPOINT con commit exacto y validation=passed;
9. emitir FINISH solo después de un checkpoint válido.

El worker event canónico es `MLS_GLOBAL_DISPATCH_EVENT`.

## Auto-pull y chats descartables

Al FINISH de un assignment R33, Worker Events crea automáticamente un claim siguiente.

Para work IDs `r33-handoff:2208:...`, el auto-pull conserva:

- `provider: r33-farm`;
- `workPrefix: r33-handoff:2208:`.

Por tanto una sesión sana puede continuar microclaim tras microclaim sin escapar al backlog general.

Si el chat se pierde, el lease puede expirar, el Global Dispatcher captura recovery y otro chat con `MLS R33 siguiente` puede continuar. No se depende de memoria conversacional.

## Estados sin trabajo

`capacity_busy`: hay trabajo del gate temporalmente leaseado. No tomar backlog externo.

`no_work`: no hay un microclaim elegible dentro del scope #2208. No reinterpretar como permiso para R33 general.

`stale_claim`: el claim superó TTL antes de adjudicación; crear uno nuevo.

`duplicate_claim`: el request ya fue visto; reutilizar el estado durable.

## Gate final

La Wave R4.3 reconciliada no pasa el gate por sí sola.

Para permitir escalamiento deben quedar contabilizadas las 100 unidades:

- first-pass VERIFIED + repairs VERIFIED = 100;
- unresolved R33 failures = 0;
- validator bypasses = 0;
- ownership duplicates = 0;
- canonical Evidence artifact verificado por commit/hash;
- sin degradar APA 7 ni Source Registry.

Solo después se evalúa el scale gate.
