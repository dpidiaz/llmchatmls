## 1. Motivación y objetivo

R4 protege el trabajo con leases, control de ownership, commits por entrada, checkpoints, recuperación y validaciones R33. Su circuito actual requiere operaciones GitHub frecuentes. La auditoría de `scripts/MLS global dispatcher scheduler.cjs` y `scripts/MLS global dispatcher worker.cjs` identificó: enumeración y reconciliación de Issues, persistencia del ledger mediante GET/PATCH/GET, comprobación del HEAD de ramas y, para checkpoints, comparación de commits y rutas. La finalización de ciertos microclaims también encadena solicitudes de autoPull.

**Objetivo R4.1:** recuperar la eficiencia de la producción por lotes sin perder la granularidad y las garantías de R33/R4. Un worker que ya dispone de una asignación válida debe poder preparar Evidence y registrar checkpoints locales sin hacer una escritura GitHub por entrada. GitHub sigue siendo la autoridad del contenido integrado, no un registro conversacional implícito.

Esta propuesta **no elimina por definición** los límites secundarios de GitHub: traslada el posible HTTP 403 a la etapa de sincronización. El circuit breaker remoto todavía es una tarea pendiente de implementación.

## 2. Arquitectura objetivo y estado real

```text
Dispatcher / asignación exclusiva confirmada
       |
       v
Export de assignment + snapshot canónico
       |
       v
ChatGPT worker -> buffer persistente exportable
                  |- manifest.json (asignación, hash)
                  |- entries/<CODE>.json (Evidence individual)
                  |- checkpoints/<CODE>.json (uno por entrada)
                  '- package.json (solo al sellar)
       |
       v
Seal: evaluación R33 en checkout canónico local
       |
       v
Plan: read-only / REMOTE_AUTHORIZATION_REQUIRED
       |
       v
[PENDIENTE] Sincronizador único -> ledger vivo -> commit agrupado -> CI -> integración
```

**Implementado:** buffer local, checkpoints inmutables, lectura e inspección, sellado sujeto a validación R33, planificación de importación **sin escritura**.  
**No implementado:** exportador automático del Dispatcher, adjudicación remota por paquetes, sincronizador con revalidación de ownership, commits agrupados, circuit breaker remoto, integración con el comando `MLS siguiente`, certificación de diez entradas académicas reales.

Los checkpoints de prueba son durables en el sistema de archivos donde se ejecuta el CLI, no mágicamente compartidos entre conversaciones de ChatGPT. Para recuperar trabajo en otra sesión es necesario conservar y volver a proporcionar **el directorio completo de staging** en almacenamiento persistente. Un contexto de chat por sí solo no cumple esta garantía.

## 4. Modelo de datos: asignación y persistencia

El CLI **no genera una reserva propia**. Solo admite un JSON presentado como export de una asignación anterior del Global Dispatcher, con:

- `allocatedBy: "global-dispatcher"`, `assignmentId`, `assignmentIssueNumber`, `leaseEpoch`.
- `poolId`, `manifestVersion`, `baseCommit` (SHA de commit) y `contentManifestBlobSha` (SHA de blob Git del manifiesto del corpus).
- Entre 1 y 100 elementos `units`, cada uno con `code`, `language`, `contentPath` y, opcionalmente, la ruta de Evidence esperada.

El formato local comprueba estructura, identidad y no duplicación, **pero no autentica por sí solo la procedencia de ese JSON ni prueba que el lease continúe vigente**. Esa autorización requiere cotejo remoto antes de cualquier integración.

`manifest.json` contiene la asignación normalizada y su `allocationHash`. Cada entrada debe coincidir exactamente con una unidad asignada, usar `architecture: "github-native"` y declarar un estado R33 reconocido. El checkpoint registra `entrySha`, ruta canónica, vínculo con `allocationHash` y `assessment: "PENDING_CANONICAL_R33_VALIDATION"`: la mera escritura del checkpoint **no certifica** el estado declarado por ChatGPT.

`package.json` se crea solo después de evaluar todas las entradas contra el checkout canónico, con hash determinista y `integration: "PENDING_REMOTE_RECONCILIATION"`. No debe etiquetarse como `INTEGRATED` ni `DEPLOYED`.

### Propiedades y límites del buffer local

- `init` repetido con asignación idéntica devuelve una respuesta idempotente; otra asignación sobre el mismo buffer se rechaza.
- Una entrada/checkpoint idéntica puede repetirse sin duplicación; una variante divergente debe resolverse explícitamente, sin overwrite.
- Se detecta un archivo de entrada existente sin checkpoint como *orphan*: puede completarse el checkpoint únicamente si el contenido coincide.
- `inspect` informa `completed`, `missing`, `orphans`, `invalid` y `sealed`; verifica coherencia de hashes y del paquete sellado.
- El bloqueo `.writer-lock` es local al directorio: **no es un lock distribuido** entre dispositivos ni conversaciones. Si queda abandonado, debe reconciliarse antes de retirarlo.
- El hash propio usa SHA-256 sobre representación JSON de claves ordenadas. No sustituye la identidad canónica de `articleHash`, `claimId`, `linkId` y `evidenceSnapshotHash`.

## 5. Uso del piloto desde un checkout local

Se requiere Node.js y una **copia canónica completa** con corpus, Source Registry y módulos R33. Los datos de asignación y Evidence deben provenir de un proceso autorizado; los nombres siguientes son ejemplos de rutas, no lotes que ya existan.

```bash
node scripts/R4-1-buffered-farm.cjs init <buffer-dir> <assignment.json>

# Ejecutar una vez por unidad asignada, persistiendo tras cada una:
node scripts/R4-1-buffered-farm.cjs checkpoint <buffer-dir> <entry.json>

node scripts/R4-1-buffered-farm.cjs inspect <buffer-dir>
node scripts/R4-1-buffered-farm.cjs seal <buffer-dir> <canonical-checkout>
node scripts/R4-1-buffered-farm.cjs plan <buffer-dir> <canonical-checkout>
```

- **init:** valida estructura de la asignación, reserva las unidades de forma local y escribe `manifest.json`.
- **checkpoint:** conserva el JSON de Evidence y el registro inmutable de **una** entrada; no contacta GitHub.
- **inspect:** detecta faltantes, corrupción, entradas huérfanas y consistencia del paquete.
- **seal:** exige buffer completo y evaluación satisfactoria de cada entrada como `VERIFIED` o `REVIEWED` mediante el validador R33 del checkout. Comprueba además las identidades canónicas de artículo, claims, links y snapshot.
- **plan:** revalida R33, comprueba que la rama no sea `main/master`, que el commit base sea ancestro, que el blob del manifiesto del corpus no haya cambiado y que los archivos ya existentes sean idénticos. **No crea commits, PRs, claims ni escrituras GitHub.**

Para migrar entre sesiones, guardar/copiar el directorio completo, incluidas las entradas y checkpoints, con sus hashes. No reutilizar asignaciones vencidas o recuperadas sin nueva comprobación del Dispatcher.

## 6. Evidence & Provenance R33: garantías preservadas

Se **reutilizan** `MLS R32 EDITORIAL/evidence git.js` y `evidence foundation.js`; R4.1 no introduce un certificador paralelo. Durante `seal`/`plan`, la implementación llama a la evaluación canónica y falla ante estado no conforme. Además contrasta el artículo y recalcula las identidades de las afirmaciones, relaciones con fuentes y snapshot.

Las categorías `UNSOURCED`, `SOURCED`, `VERIFIED` y `REVIEWED` mantienen el significado R33. Nunca debe inventarse un DOI, un ISBN, un locator o una referencia APA 7 para superar el gate. Las comprobaciones automáticas de estructura y cobertura no son una garantía independiente de verdad factual; debe verificarse que las fuentes respaldan efectivamente las afirmaciones. El preflight R4 existente continúa siendo una referencia canónica y no fue eliminado.

## 7. Fallos y protocolo de recuperación

| Situación | Comportamiento ya probado o esperado |
| --- | --- |
| Chat/worker termina antes de persistir | El razonamiento no persistido no es recuperable; no atribuirle progreso. |
| Interrupción tras escribir entrada y antes de checkpoint | `inspect` detecta orphan; recuperación exacta si coincide el JSON. **Probado**. |
| Repetición de checkpoint idéntico | Replay sin crear segunda entrada. **Probado**. |
| Checkpoint o entrada alterados | Invalida inspección y bloquea `seal`. **Probado**. |
| Falta una entrada | `seal` falla cerrado. **Probado**. |
| El evaluador no certifica R33 | `seal` falla cerrado. **Probado con doble de prueba**. |
| El manifiesto del corpus se movió | `plan` rechaza importación. **Probado con estado Git simulado**. |
| Rama protegida, base divergente o archivo canónico distinto | `plan` rechaza importación. **Probado con estado Git simulado**. |
| HTTP 403 / Secondary Rate Limit durante sincronización | **Pendiente:** circuito remoto debe conservar paquetes, respetar `Retry-After` y detener reintentos simultáneos. |
| Lease expirado, ownership duplicado, conflicto con #1433/#1458 | **Pendiente:** cotejo contra ledger y ramas vivas antes de aprobar importación. |
| Fallo durante commit remoto agrupado | **Pendiente:** relectura/reconciliación por hash y SHA exactos; no marcar como integrado por presunción. |

## 9. Trabajo pendiente (bloquea la adopción de R4.1)

1. Exportador/adaptador del Allocator: emitir reservas de buffer exclusivas, verificables y compatibles con el ledger actual, sin crear un lease falso ni reutilizar trabajos expirados.
2. Persistencia compartida o exportación/importación operacional del staging entre chats, con recuperación y exclusión de writers comprobadas en el entorno elegido.
3. Sincronizador remoto **single-writer**, con relectura de ledger, assignments y epochs; reconciliación de terminales, recoveries, collisiones y corpus; commit agrupado idempotente y confirmación exacta del SHA.
4. Circuit breaker explícito para HTTP 403 y respeto de límites GitHub; no reintentos automáticos masivos desde workers.
5. Piloto de **diez entradas reales** con fuentes verificadas y comparación de llamadas remotas antes/después; gates posteriores 25 → 50 → 100 solo tras aprobar integridad, evidencia y recuperación.
6. Adaptar la ruta `MLS siguiente` únicamente después de certificación y autorización de integración. Hasta entonces sigue utilizando R4 vigente.
