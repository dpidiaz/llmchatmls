## 1. Contexto y propósito

R4 hacía bien varias cosas: exclusión por leases y locks, checkpoints por entrada, preservación de commits huérfanos, R33 Evidence/Provenance y publicación diferida. El cuello de botella era el contacto remoto por cada unidad: enumeración de Issues, creación/asignación de claim, comprobaciones de branch HEAD y compare, escritura del ledger mediante GET/PATCH/GET, evento de checkpoint y siguiente autoPull. Un HTTP 403 Secondary Rate Limit detenía el proceso editorial.

R4.1 desacopla **granularidad editorial** (checkpoint individual) de **frecuencia de transmisión remota** (una reserva y un paquete de sincronización por 10/25/50/100 entradas). No borra Dispatcher, Source Registry, R33 ni los índices existentes.

```text
   Colaborador autorizado -> [MLS Buffered][REQUEST] (una vez por lote)
                                       |
                    Scheduler Global serializado / Allocation
                                       |
                           [MLS Buffered][RESERVED]
                                       |
                     ChatGPT + staging durable exportable
                     |-- manifest.json
                     |-- entries/MLS-....json
                     |-- checkpoints/MLS-....json (1/entrada)
                     '-- package.json (sellado R33)
                                       |
                          export -> r41-package.json
                                       |
                 GitHub rama r41/inbox/<Issue> (un blob)
                                       |
                   [MLS Buffered][SYNC] (una vez por paquete)
                                       |
                     R4.1 Buffered Sync (concurrency:
                           mls-global-dispatcher)
                      |-- fetch bundle
                      |-- revalidar ownership, corpus, R33
                      |-- staged branch r41/staged/<Issue>
                      |-- validadores + commit único por lote
                      '-- comprobar SHA exacto / STAGED
                                       |
                         Scheduler al concluir CI
                      |-- verificar workflow/commit/paths
                      |-- registrar terminal certificado
                      |-- cerrar reserva y sync request
                      '-- publicación final R4 diferida
```

**Diferencia conceptual:** GitHub sigue siendo la autoridad del corpus integrado y de la reserva entre sesiones. El chat produce temporalmente contra una asignación ya exclusiva; su memoria nunca se considera almacenamiento transaccional. Una reserva R4.1 permanece protegida aun cuando caduque el lease temporal de un chat. El release es explícito y exige revisión de recuperación.

## 3. Operativa: contrato preciso de asignación

Una petición debe originarla el owner, MEMBER o COLLABORATOR autorizado del repositorio (no cualquier autor de Issues públicos).

**Título:** `[MLS Buffered][REQUEST] <identificador humano>`  
**Marcador en el cuerpo:**

```text
<!-- MLS_BUFFERED_REQUEST
{"kind":"mls_buffer_request","version":1,
 "requestId":"buffer-20260929-001","mode":"reserve","size":10}
-->
```

Tamaños permitidos: 10, 25, 50, 100; la cantidad solicitada debe existir de forma íntegra y disponible o el proceso falla cerrado, sin reserva parcial. El Scheduler serializado lee el pool y sus ledgers, termina/reconcilia trabajos vencidos, comprueba el HEAD fresco de `main`, el blob `content/manifest.json` y adjudica unidades elegibles una sola vez; transforma el Issue original en `[MLS Buffered][RESERVED] MLS-BUFFER-<Issue>`.

El Issue contiene un bloque `MLS_BUFFERED_RESERVATION` con `allocation` y `allocationHash`. Es preciso transferir **ese objeto allocation** como `assignment.json` al worker, sin construir IDs ad hoc. El buffer verifica `assignmentIssueNumber`, `leaseEpoch`, `poolId`, `manifestVersion`, `baseCommit`, `contentManifestBlobSha`, idioma, code, contentPath y Evidence path por unidad. Esta validación de formato local no sustituye la relectura autorizada remota.

Los estados `RESERVED`, `STAGED` y `QUARANTINED` bloquean nuevos claims de esos códigos sin depender del TTL del chat. El proveedor también protege recoveries R4 anteriores, incluidos trabajos huérfanos, contra regeneración. Si el ledger está corrupto, hay ownership doble o una reserva inválida, se debe fallar cerrado.

**Liberación excepcional (manual, con revisión de recuperación):**

```text
<!-- MLS_BUFFERED_REQUEST
{"kind":"mls_buffer_request","version":1,
 "requestId":"release-20260929-001","mode":"release",
 "targetIssueNumber":1234,"recoveryReviewed":true,
 "reason":"Se revisó y recuperó todo progreso del buffer."}
-->
```

No se borra automáticamente progreso de una conversación simplemente por caducidad de su lease temporal.

## 4. Worker: CLI y formato recuperable

Todos los comandos siguientes son locales; no usan GitHub REST:

```bash
node scripts/R4-1-buffered-farm.cjs init <buffer> <assignment.json>
node scripts/R4-1-buffered-farm.cjs checkpoint <buffer> <evidence-entry.json>
node scripts/R4-1-buffered-farm.cjs inspect <buffer>
node scripts/R4-1-buffered-farm.cjs seal <buffer> <canonical-checkout>
node scripts/R4-1-buffered-farm.cjs plan <buffer> <canonical-checkout>
node scripts/R4-1-buffered-farm.cjs export <buffer> <bundle.json>
node scripts/R4-1-buffered-farm.cjs import <buffer> <bundle.json>
```

`manifest.json` identifica la reserva y su hash. `entries/<CODE>.json` conserva una unidad. `checkpoints/<CODE>.json` incluye hash, ruta, estado pendiente de evaluación y asignación exacta; `checkpointSizeMax=1` sigue vigente. Si se interrumpe una sesión tras escribir la entrada antes del checkpoint, `inspect` registra un *orphan* y únicamente acepta la continuación si coinciden exactamente los bytes lógicos/hash.

`seal` exige un checkout canónico completo (contenido original + Source Registry y herramientas R33); llama a `evidence git.js` y recalcula/verifica los IDs del artículo, claims, EvidenceLinks y snapshot. Solo se sella el paquete cuando todas las entradas alcanzan legítimamente `VERIFIED` o `REVIEWED` y la evaluación canónica aprueba. Una marca textual de ChatGPT no equivale a certificación. **Las fuentes nuevas aún no presentes en el Source Registry canónico deben incorporarse mediante el protocolo R33 existente antes del sellado.** No se inventan DOI, localizadores, ISBN o referencias APA.

`export` produce **un único archivo JSON** inmutable y autoconsistente que incluye manifiesto, entradas, checkpoints, paquete y `bundleHash`; `import` comprueba todos sus componentes y reconstruye el staging de forma aislada, rechazando diferencias. Conservar copia externa del bundle y/o directorio completo; distintas conversaciones NO comparten automáticamente un sistema de archivos ni una memoria de cambios confirmados.

## 5. Sincronización diferida de un paquete

Requiere que la funcionalidad de Issues/workflows esté **integrada en el branch predeterminado**. En la PR Draft actual, el código está presente pero esta activación real sigue pendiente.

1. Preparar desde Chat/CLI una rama de inbox `r41/inbox/<reservationIssueNumber>` basada en el snapshot correspondiente, con **un archivo** en la raíz denominado `r41-package.json` cuyo contenido es el bundle exportado. No crear un Issue/commit por entrada.
2. Crear un Issue de un colaborador autorizado con título `[MLS Buffered][SYNC] <paquete>` y marcador exacto:

```text
<!-- MLS_BUFFERED_SYNC_REQUEST
{"kind":"mls_buffer_sync_request","version":1,
 "reservationIssueNumber":1234,"inboxBranch":"r41/inbox/1234"}
-->
```

**Aislamiento del snapshot en reintentos:** el workflow crea un checkout canónico independiente de la rama de staging (worktree detached de `main`) y pasa su ruta como `MLS_R41_CANONICAL_ROOT`. El proveedor R33 calcula elegibilidad exclusivamente contra ese checkout canónico; `prepare` y `mark` pueden releer la rama de staging aunque ya contenga los Evidence del paquete, sin confundirlos con entradas previamente integradas. La prueba de regresión comprueba tanto el contrato del workflow como el argumento `canonicalRoot` de `verifyLive`.\n\n3. `R4.1 Buffered Sync` se ejecuta bajo **la misma** concurrencia `mls-global-dispatcher` que el Allocator. Importa el bundle, rehace el snapshot contra GitHub, impide conflictos de ledger/claims/recoveries/DONE, exige mismo artículo y hashes y crea/reutiliza `r41/staged/<Issue>`, sin escribir a `main`.
4. Ejecuta validación R33 canónica y pruebas editoriales; hace commit agrupado del subconjunto realmente nuevo/modificado y push **sin force**. Si todas las rutas ya eran idénticas y es el primer stage, crea un commit vacío identificable del batch; reintentos de stage idéntico pueden reutilizar el commit confirmado. Nunca incluye archivos ajenos al assignment.
5. Comprueba por API el SHA exacto del branch de staging; transforma el Issue original a `STAGED` con `packageHash`, `workflowRunId`, `syncRequestIssueNumber` y commit exacto.
6. Al terminar el workflow, el Scheduler verifica que el run **terminó con éxito**, confirma branch/commit/parent, mensaje de commit, **solo archivos asignados** y descendencia, revisa terminales y recoveries otra vez. Solo entonces guarda el terminal `status: certified` del lote en el ledger, con refs de las unidades, cierra la reserva `DONE` y después el Issue original `SYNCED`.

`CERTIFIED_STAGED` significa contenido auditado y localizable por branch/SHA dentro del circuito R4 de integración diferida. **No significa merge de Evidence a `main` ni despliegue Cloudflare.** Los pasos de publicación final existentes siguen siendo independientes y sujetos a su certificación.

## 6. HTTP 403, recuperación, duplicados e idempotencia

- Ante HTTP 403/429 el cliente remoto devuelve `SYNC_BLOCKED`, conserva la información `Retry-After` cuando existe y **no reintenta automáticamente**. El workflow termina, pero no borra el buffer ni libera ownership; el usuario puede volver a solicitar sincronización después de que corresponda.
- **Disciplina de cola:** enviar como máximo un Issue `[MLS Buffered][SYNC]` por vez. GitHub Actions puede reemplazar un run pendiente durante ráfagas del mismo grupo de concurrencia; una ejecución sustituida NO autoriza borrar la reserva. Tras comprobar que no hay sincronización activa, puede crearse un nuevo Issue para el mismo paquete. Cuando uno termina certificado, el Scheduler cierra los anteriores del mismo paquete como `SUPERSEDED`. Nunca lanzar sincronizaciones masivas desde chats independientes.
- Una reserva `STAGED` no admite liberación manual antes de reconciliar el resultado de CI en el ledger; `QUARANTINED` conserva la exclusión hasta recuperación o release explícito con revisión.
- El único writer de reserva, sincronización y finalización usa `concurrency.group: mls-global-dispatcher`. El lock de `r4 buffered core.cjs` es **local al directorio**, no distribuido: la exclusión entre chats descansa en las reservas remotas, no en supuesta memoria compartida.
- Un Issue `STAGED` con workflow fallido se convierte en `QUARANTINED` preservando propiedad. Se admite revalidar el MISMO packageHash y commit en un nuevo run; diferencias requieren reconciliación explícita.
- Los checks exactos evitan aplicar una asignación a un corpus desplazado, apuntar a una rama protegida, adjudicar un código terminal/recuperable o aceptar una segunda versión contradictoria.
- Cualquier commit remoto parcial o resultado incierto obliga a releer SHA y estado vivo; no se declara `DONE` por el solo hecho de emitir un push.
- No se retiran índices ni se regeneran índices globales desde workers.

### Modelo de estados

`UNSOURCED/SOURCED/VERIFIED/REVIEWED` son dimensiones **editoriales** R33; `RESERVED/STAGED/QUARANTINED/DONE` son estados **operativos** del paquete. `DEPLOYED` requiere confirmación separada del pipeline de publicación.

## 8. Activación, rollback y límites residuales

**No activar automáticamente.** Hasta revisión y autorización explícita del merge, `MLS siguiente` sigue usando la ruta R4 antigua; no hay migración silenciosa de claims o checkpoints antiguos. La apertura de nuevos Issues de buffer y la ejecución real de sync Issue-workflow necesitan que sus definiciones estén en la rama predeterminada. Una vez fusionado, comenzar con una reserva real de 10 unidades, con evidencia comprobable de exclusión, integridad y conteo remoto; solo después escalar a 25 → 50 → 100.

**Rollback pre-merge:** mantener la PR en Draft/cerrarla; no afecta `main` ni Cloudflare.  
**Rollback tras merge futuro:** dejar de crear Issues `[MLS Buffered][REQUEST]` y `[SYNC]`, preservar o revisar cada reserva existente hasta cerrar sus recuperaciones; mantener intacto R4 y desactivar triggers solo mediante nuevo cambio autorizado.

**Riesgos que no desaparecen:** precisión factual de IA, comprobación bibliográfica externa, pérdida del contenido que solo esté en memoria del chat, revalidación cuando cambie corpus/pool, rate limit durante la sincronización, cola de paquetes pendientes y disponibilidad de almacenamiento persistente para bundles. Los estados de validación de R33 son controles verificables, no promesas de infalibilidad académica.

**FREE ONLY irrevocable:** ningún OpenAI API ni otra API de IA pagada, ni claves/opciones latentes para activarlas en el futuro. Solamente Chat para edición, archivos exportables, integración GitHub y CI ya existentes. No escribir datos editoriales en D1/Cloudflare.
