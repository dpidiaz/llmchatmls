# MLS R4.1 — Batch Context Reuse (BCR-1.0)

**Política:** SOLO CHAT · FREE ONLY absoluto · GitHub canónico · sin OpenAI API, proveedores comerciales, D1 editorial o Cloudflare editorial. El circuito **normal** \`MLS siguiente\` mantiene R4. BCR solo actúa en el opt-in de Buffered Farm R4.1. No cambia R33 ni el Dispatcher. Tamaño máximo de una reserva nueva: **25**, cinco bloques de cinco; no hay Gate 50/100 en la política vigente.

## Diagnóstico dirigido del circuito previo

R4.1 ya permite reservar identidades de forma exclusiva desde el Scheduler, guardar checkpoints inmutables y sincronizar **todo** el paquete mediante un commit agrupado. Sus piezas son \`r4 buffered core.cjs\`, \`r4 buffered sync.cjs\`, \`r4 buffered academic.cjs\` y \`r4 buffered transport.cjs\`. Entre chats faltaba un índice compacto versionado: el operador reconstruía desde \`manifest.json\`, \`progress.json\`, varios checkpoints y búsquedas bibliográficas ya efectuadas. Se mantiene la certificación **independiente de cada artículo**. Reducir lecturas no elimina los Secondary Rate Limits.

## Arquitectura aditiva

### A. Fixed Batch Recipe

\`MLS R32 EDITORIAL/r4 buffered context.cjs\` exporta \`RECIPE\`, \`VERSION\` y \`RECIPE_HASH\` (hash SHA-256 determinista con el contrato \`core.hash\`). La receta recuerda R33, APA 7, la distinción entre evidencia y sugerencias bibliográficas, seguridad FREE ONLY, concurrencia y recuperación. Se carga una vez por sesión. Su alteración invalida los Context Packs antiguos: migrar/reconstruir mediante checkpoints existentes, no silenciar el conflicto.

### B. Context Pack y Source Index

Ambos se guardan, separados de las entradas completas, bajo el prefijo **no canónico** \`r41-buffer/<issue>/bcr/\` de la rama dedicada a esa reserva:

| Archivo | Contrato |
| --- | --- |
| \`bcr/recipe.json\` | Receta fija; versión/hash recalculable. |
| \`bcr/context-pack.json\` | Identidad y snapshot de la reserva; 25/5; \`recipeHash\`, \`allocationHash\`, progreso; lista de códigos y hashes de checkpoints; refs de Source Index, delta y padre confirmado; \`stateHash\`. **Nunca artículos completos**. |
| \`bcr/source-index.json\` | Fuente por identificador estable, clave bibliográfica DOI/ISBN/URL normalizada, metadatos, SHA de blob del registro canónico, localizadores reutilizables, pares \`code/claimId/linkId\`. Marca \`REGISTERED_REFERENCE_ONLY\` y \`entryVerificationInherited:false\`. |
| \`bcr/deltas/block-0N.json\` | Códigos, hashes, fuentes añadidas/reutilizadas, hash del Context Pack previo y actual; incidencias; commit padre, sin inventar el SHA del propio commit. |
| \`bcr/handoff.md\` | Resumen para continuar otro chat, código siguiente, hashes, archivos y límites académicos. |

La fuente puede reutilizarse como **pista de consulta**. Cada nuevo claim exige comprobar que el apartado realmente lo respalda y ejecutar otra vez R33 y el gate académico. La deduplicación de identidad bibliográfica no deduplica verificaciones de afirmaciones. Todo registro cambiante invalida el pack mediante su \`registryFingerprint\` y \`registryBlobSha\`.

### C. Progressive Block Delta

El bloque siguiente recupera el último Context Pack y Source Index, su delta indicado, \`manifest.json\`, \`progress.json\` y **solo sus cinco nuevos artículos**; verifica hashes/versiones antes de producir. El progreso anterior se hereda como cinco punteros a checkpoints, no como cinco artículos cargados otra vez. Si falta Context Pack, se reconstruye **determinísticamente** del manifiesto, chunk confirmado, checkpoints y Source Registry. Un delta incompleto no modifica el estado válido anterior. Repetir un bloque idéntico devuelve \`replayed:true\`; uno alterado o fuera de orden se rechaza.

## Particularidad técnica del commit y recuperación

Un commit Git no puede incluir su propio SHA dentro de los archivos que lo componen sin crear una dependencia circular. Por ello el Context Pack guarda el **commit padre remotamente confirmado**, \`commitConfirmation: REQUIRES_REMOTE_REF_READBACK\` y su propio \`stateHash\`; después del único commit agrupado, la persona/Chat comprueba la ref remota y comunica el SHA del nuevo HEAD en el handoff del chat. **Nunca declarar persistente un archivo local sin lectura de la ref.**

El adaptador local \`scripts/R4-1-bcr.cjs\` tiene operaciones \`bootstrap\`, \`advance\`, \`verify\` y \`next\`. Opera solo sobre archivos locales y no usa una API ni red. Su salida dice \`preparedLocally:true, remotePersisted:false\`; el escritor de Chat o repositorio hace el commit Git agrupado con control optimista de HEAD. \`commitOptimistic\` proporciona una interfaz de un único write, una lectura previa y una confirmación posterior; en 403/429 corta sin reintentos y expone \`exportUnconfirmed\` cuando el trabajo quedó únicamente local.

Al avanzar un bloque, el adaptador prepara los cinco Evidence, cinco checkpoints, chunk portable, progreso y metadatos compactos en un único conjunto lógico de archivos. **No** se sella un paquete \`MLS-R4.1-BUNDLE-1\` antes de 25/25 ni se abre Issue SYNC hasta superar \`canonicalAssessment\`, validación por sección y verificación remota de la reserva.

## Medición y seguridad

Capturar por bloque: lecturas y escrituras instrumentadas de GitHub (incluidas una verificación anterior y otra posterior), número de commits, volumen de Context Pack, fuentes conocidas y nuevas, reused hints, códigos completados, errores y conflictos. Las llamadas de conectores de Chat no deben confundirse con la métrica instrumentada de GitHub Actions. Si el ahorro no está respaldado por una comparación equivalente, no declarar una reducción porcentual. No reintentar automáticamente un HTTP 403/429.

Los tests \`test/r4 buffered bcr.test.cjs\` cubren T01–T14 del prompt maestro: inicialización, recuperación compacta, no transferencia de \`VERIFIED\`, commits agrupados, idempotencia, caída parcial, 403, concurrencia, invalidez de versión/fuente, sellado 25, R4 intacto, FREE ONLY, provenance y exportación no confirmada.
