# MLS-SND — Objetivo persistente

## Objetivo canónico

Desarrollar de forma autónoma y continua el tomo independiente **MLS-SND — Pronunciación y sistemas sonoros** hasta llevarlo a una versión editorialmente completa, lingüísticamente rigurosa, auditable y lista para composición, coordinando múltiples chats/branches mediante GitHub.

## Reglas permanentes

1. **No modificar los tomos existentes** salvo autorización expresa.
2. **R32** inspira estructura editorial, modularidad, títulos y entradas consultables.
3. **R33** gobierna evidencia, procedencia, localizadores y validación afirmación por afirmación.
4. **R44** organiza unidades de trabajo, dependencias y entregas; no define contenido lingüístico.
5. No inventar pronunciaciones, reglas, equivalencias fonéticas ni variedades.
6. Mantener explícito el alcance de cada afirmación: idioma, variedad, contexto y fecha cuando sean materiales.
7. Tratar IPA/AFI como herramienta descriptiva compartida, no como idioma ni sustituto de ortografías o sistemas locales.
8. Priorizar fuentes institucionales y académicas verificables, con APA 7 y localizadores exactos.
9. Distinguir redacción editorial de validación lingüística/evidencial.
10. El tomo debe funcionar plenamente como obra escrita, sin depender de audio, ASR, ejercicios, pruebas o evaluaciones.

## Protocolo para chats/branches

Cada chat que trabaje en MLS-SND debe:

1. leer este archivo;
2. leer `STATUS.md`, `MLS-SND-MASTER-INVENTORY.md`, `MLS-SND-SOURCE-REGISTRY.md` y las políticas editoriales;
3. revisar ramas/PRs recientes para evitar duplicación innecesaria;
4. elegir trabajo útil y desbloqueado;
5. crear o utilizar una rama GitHub propia;
6. investigar, redactar, auditar o revisar según el área elegida;
7. hacer commits pequeños y claros;
8. abrir PR hacia `feat/mls-snd-foundation`, no directamente hacia `main`;
9. registrar qué quedó hecho, qué claims fueron validados, qué sigue abierto y qué decisiones requieren integración;
10. al terminar un bloque, tomar el siguiente trabajo útil sin esperar una nueva instrucción manual.

## Regla de coordinación

GitHub es la memoria compartida y el protocolo de coordinación entre chats.

No se requiere que los chats se comuniquen directamente entre sí. La coordinación ocurre leyendo:

- ramas;
- commits;
- PRs;
- `STATUS.md`;
- el inventario maestro;
- el Source Registry;
- decisiones editoriales ya fusionadas.

Si dos chats trabajan accidentalmente el mismo tema, el segundo resultado puede servir como revisión independiente. No se debe sobrescribir silenciosamente trabajo ajeno.

## Definición de “continuar”

“Continuar” significa:

- tomar trabajo desbloqueado;
- reducir huecos de evidencia;
- redactar entradas cuando exista base suficiente;
- auditar claims;
- resolver inconsistencias;
- mejorar referencias cruzadas;
- fortalecer variedad/transcripción;
- preparar contenido para composición.

No significa generar texto en masa sin fuentes ni rebajar gates para aumentar throughput.

## Condición de finalización del objetivo

El objetivo se considera cumplido cuando:

1. la arquitectura del tomo está congelada;
2. todas las unidades necesarias están redactadas;
3. las afirmaciones materiales están respaldadas y auditadas;
4. las variedades y convenciones de transcripción están explícitas;
5. las entradas han pasado revisión lingüística/evidencial y editorial;
6. referencias cruzadas, glosario, índices y bibliografías están completos;
7. el manuscrito está listo para composición;
8. no quedan bloqueos críticos conocidos sin documentar.

Hasta entonces, el estado del proyecto es **ACTIVE**.
